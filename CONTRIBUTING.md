# Contributing

Thank you for improving Kaitersberg. Small, focused changes are easiest to review.
For a new skill, a change to a pipeline invariant or another broad change, open an
issue first so the shape can be agreed before both sides invest in an implementation.
Forks and experiments are welcome; there is no expectation that a fork stays
compatible. When a change is useful beyond one fork, an upstream issue or pull
request is especially appreciated.

By submitting a contribution, you agree that it is licensed under this repository's
[MIT License](LICENSE) and that you have the right to submit it.

Everything a change to this repository has to satisfy is one command:

```bash
git config core.hooksPath .githooks   # once per clone
scripts/check.sh                      # what the pre-commit hook runs
```

See [Working on this repository](README.md#working-on-this-repository) in the README
for what it checks and why.

## What a change looks like here

- **Do not develop on `main`.** Use a branch and its own worktree. This keeps skill
  work isolated from local plugin cachebusters and from other changes in flight.
- **Edit `.claude/skills/` only.** `.agents/skills/` and both plugin skill trees are
  generated by `scripts/port-to-codex.py`. Commit the regenerated trees with the
  change; a stale port is worse than none.
- **Every rule carries its reason.** A rule without one is followed until somebody
  finds it inconvenient. This is the single most important convention in the
  repository, and [CLAUDE.md](CLAUDE.md) states the rest.
- **Skills are English**, whatever language the documents they produce are in.
  `scripts/lint-skills.py` enforces it, along with frontmatter, resolvable links and
  handoffs that name a skill which exists.
- **Commit messages**: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:` or
  `revert:`, no full stop, a blank line before the body. The `commit-msg` hook
  checks it. Say what changed and why it was wrong before; the body is where the
  reasoning of this project lives.
- **Do not commit a `+codex.local-` version.** That cachebuster belongs to a local
  install; the hook refuses it.
- **Update the documentation that became false.** A checked README or process
  document that still tells the old story is part of the defect.

## Pull requests

Before opening a pull request:

1. Rebase or merge the current `main` into the branch and resolve generated-tree
   changes by editing the source and regenerating, never by hand.
2. Run `scripts/check.sh` from the repository root.
3. Explain the problem, the chosen change and the verification in the pull request.
4. Link the issue when one exists and call out security, migration, compatibility
   or release-version consequences explicitly.

`ruff.toml` deliberately names the Python lint rules. Do not broaden that set as a
side effect of upgrading Ruff: enable additional rule families in a focused change
that fixes or consciously configures every new finding.

AI-assisted contributions are welcome. The person opening the pull request owns
the result: read the generated diff, remove unrelated changes and be able to explain
why every changed rule or script is correct.

## Privacy when contributing

Issues, pull requests, reviews and commit metadata become public when the repository
is public and may remain available in Git history after a branch or file is removed.
Use a [GitHub-provided `noreply` address](https://docs.github.com/en/account-and-profile/concepts/email-addresses)
if you do not want a personal email address in commits. Do not submit customer data,
private product artefacts, credentials or personal data about somebody else. GitHub
processes account and usage data under its own
[privacy statement](https://docs.github.com/en/site-policy/privacy-policies/github-general-privacy-statement).

If personal or secret data is committed accidentally, stop sharing the commit and
use the private reporting route in [SECURITY.md](SECURITY.md). Deleting the file in
a later commit is not sufficient because the earlier object remains in history.

## Changing a skill

Read the skill you are changing, in full, before editing it. The phases depend on
each other, the checklists mirror the phases, and the handoff at the end is what the
next skill reads. Then run the port, and check that the invariants in
[CLAUDE.md](CLAUDE.md) still hold: one status rung per skill, the file paths, and
that every referenced template exists.

## Conduct and security

Participation is governed by the [Code of Conduct](CODE_OF_CONDUCT.md). Report
security vulnerabilities through the private route in [SECURITY.md](SECURITY.md),
not in an issue, discussion or pull request.
